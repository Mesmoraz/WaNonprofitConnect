This page explains the whole system to someone who has never seen it — what each part is, why it exists, and how the parts talk to each other. No programming knowledge assumed.

The idea in one paragraph

Every nonprofit in Washington already exists in a public list kept by the IRS. Instead of asking 35,000 organizations to sign up, we start from that list. A person who works at one of them claims it, says what the organization needs or has, and the system finds other organizations (or businesses, or neighbors) who fit — then lets the two sides talk and hand things off. The map shows those hand-offs as threads between places, so anyone can see help moving around the state.

IRS public files

The IRS publishes a spreadsheet of every tax-exempt organization, one file per state, updated monthly. It is free and public. For Washington it has 42,510 rows; 35,361 are 501(c)(3) charities. This is the only place organizations come from — nobody types them in.

Importer

A small program that downloads that file, checks whether it changed since last time (by fingerprinting it), and updates the database organization by organization. It logs every run: which file, how many rows added or changed. It never deletes an organization that disappears from the file — it flags it.

Database

Where everything is stored: the organizations, plus everything people create — listings (needs and offers), connections between listings, messages, and later accounts. Think of it as a set of linked spreadsheets that many people can safely use at once.

API

“Application Programming Interface” — in practice, a list of web addresses (endpoints) that apps call to read or change data, each with a clear job: “search organizations”, “post a need”, “accept this connection”. Because every screen goes through the same door, a phone app, a website and a robot all behave identically, and the rules (who may accept a match, what a P0 means) live in exactly one place.

Phone / website

The screens people use. Today that is the clickable prototype; the real app will be the same screens wired to the API. It holds no rules of its own — it asks the API and shows the answer.

Command-line demo

A text-only way to drive the API from a terminal (“post this need as Ballard Food Bank”). It exists to prove the API works without a screen, and to run the whole story end-to-end in one command.

Real-time feed

Normally an app has to keep asking “anything new?”. Instead, the server keeps a line open and pushes events the moment they happen: a listing was posted, a connection was proposed, a message arrived. Public events go to everyone; private ones (matches, messages) only to the two organizations involved.

Where the organizations come from

The IRS file gives us, for each organization:

EIN
Employer Identification Number — the organization’s permanent ID, like a Social Security number for a company. We use it as the one true identifier so an org can never be duplicated. Shown as 91-1428805.
Name, address, ZIP
As registered with the IRS. The ZIP places the pin on the map (neighborhood-accurate, not door-accurate).
Subsection
Which part of the tax code the org falls under. “03” means 501(c)(3) — a charity that can receive tax-deductible gifts. Only these can use the exchange as nonprofits.
Foundation code
Tells a public charity (a food bank) from a private foundation (a family grant-maker). Foundations give money; they rarely need plywood — so the app treats them differently.
NTEE code
The cause category: K = food, L = housing, B = education, and so on. About one in five WA orgs has none, and some are wrong (a food bank coded “unknown”), which is why organizations can fix their own tags later.
Revenue, filing type
Size, and whether they file a full return or the tiny “e-Postcard” (under $50k a year). About 70% of WA charities are small enough to report no financials at all.
What the IRS file does not have: phone, email, or website. Those come from other IRS files (the e-Postcard has a website), from the WA Secretary of State registry, or — most reliably — from the organization itself once someone claims it.

Refresh: monthly. The importer only writes when the file actually changed, and it never overwrites anything a verified member typed. Every screen states which file it came from.

Listing
One thing an organization needs or has: a title, a category (Materials, Technology, Food, Volunteers, Space…), quantity, tags, and for needs a priority and for anything a cadence.
Priority
P0 can’t operate without it · P1 needed this week · P2 this month · P3 whenever. Each org may hold at most two P0s per month so the word keeps meaning something.
Cadence
One-time, weekly, monthly, quarterly, or ongoing. A recurring pair, once accepted, becomes a standing agreement: it has a next date, each delivery is logged, and either side can end it.
Connection (match)
One Need paired with one Offer. It starts Proposed; only the other organization can accept. Accepted listings are held (nobody else can match them); completing marks both fulfilled; cancelling reopens both.
Thread
Messages inside a connection. Only the two parties can read or write. Nothing here is broadcast.

How matching and fairness work

Matching is deliberately simple and explainable. For a need, every open offer is scored, and the score comes with its reasons. Ballard Food Bank’s laptop need against Computers 4 People’s laptop offer:

Same category (Technology)+50 Shared words: laptop, computer+35 Different cities, different areas+0 Need is P0+10 Offer covers the full quantity (15 ≥ 12)+10 Offer posted in the last 30 days+5 Match score110

Anything under 15 is not shown. Organizations are also alerted by their profile tags (“we often have: laptops”) even when they have no offer posted yet.

Fairness rules for the board. Listings are ordered by priority first, then by fewest views — so within a priority band the least-seen listing rises, like a rotation. No organization holds more than 2 of the top 6. One top slot always goes to the least-seen listing overall. Every card says why it’s there, and every organization can see its own exposure against the average. Sponsored content is labeled and lives outside this ranking; placement cannot be bought.

The map

Pins
One per organization, at its ZIP code. Green = nonprofit, blue = business, purple = community member. A pin grows with its number of connections when you hover it.
Clusters
Zoomed out, nearby pins merge into a numbered circle (“Seattle area · 25 orgs”). Tap it to zoom in and it splits. The glow behind a circle is its activity.
Threads
A curved string between two organizations that are connected. Gold = completed, green = in progress, amber dashed = proposed, grey dotted = suggested by matching. At rest they are faint; select one (tap it, or pick it from the Connections list) and it lights up, the dash drifts from giver to receiver and a dot travels the same way — that motion is the direction.
Filters
Needs/offers, who is posting, category, distance from you, and which connection states to show. The same filters drive the Board, so the list and the map always agree.
Scale bar
Bottom-left, in miles, re-labels itself as you zoom (1× to 40×).

Every endpoint

An endpoint is one web address with one job. GET reads, POST changes something. Anyone can read organization data; changing anything requires saying which organization you act for (today a header called X-Org-Ein; later a real login). The API runs at http://localhost:5253 in development and documents itself at /swagger.

Organizations (public data)

EndpointWhat it does
GET/api/v1/orgsSearch organizations. Filters: q (words in the name, or a 9-digit EIN), city, zip, ntee (a letter like K or a full code like K31), foundation, only501c3 (default true), excludePrivateFoundations, minRevenue/maxRevenue, page/pageSize. Returns a page of short records.
GET /api/v1/orgs?q=food+bank&city=Seattle
GET/api/v1/orgs/{ein}One organization in full, every IRS code translated to words, plus links to ProPublica and the IRS lookup. Never includes the “in care of” person’s name.
GET /api/v1/orgs/91-1428805
GET/api/v1/statsCounts: how many orgs, how many 501(c)(3)s, by cause, by size, by city, by filing type. Answers “how much is out there?”
GET/api/v1/nteeThe 26 cause categories (A–Z) with their names, for building filters.
GET/api/v1/codesEvery IRS code table the API translates (subsection, foundation, filing requirement…) so a screen can show words instead of codes.
GET/api/v1/importsThe import log: which IRS file, when, its fingerprint, rows added and changed. This is how you know how fresh the data is.
GET/health“Healthy” if the API can reach its database. Used by monitoring.

Listings (needs and offers)

EndpointWhat it does
GET/api/v1/listingsThe board. Filters: kind (Need/Offer), category, status (default Open), city, orgEin, q (keywords). Most urgent and newest first.
POST/api/v1/listingsPost a need or an offer as the acting organization. Body: kind, category, title, description, quantity, unit, urgency, tags, expiry. The org’s city and ZIP are attached automatically. Everyone whose listings or tags fit is alerted.
POST /api/v1/listings (X-Org-Ein: 911428805)
{ "kind":"Need", "category":"Technology", "title":"Laptops for client intake stations", "quantity":12, "unit":"laptops", "urgency":"Critical", "tags":"laptops,computers" }
GET/api/v1/listings/{id}One listing in full.
GET/api/v1/listings/{id}/matchesThe best counterparts for this listing (offers for a need, needs for an offer), each with a score and its reasons in plain English.
POST/api/v1/listings/{id}/closeThe posting organization takes it down.

Connections (matches) and messages

EndpointWhat it does
GET/api/v1/matchesThe acting organization’s inbox: every connection it is part of, with messages.
POST/api/v1/matchesPropose a connection between a need and an offer. You must own one of the two. Body: needListingId, offerListingId, optional note.
GET/api/v1/matches/{id}One connection with its thread. Only the two parties may read it.
POST/api/v1/matches/{id}/acceptThe other side accepts. Both listings become Matched. The proposer cannot accept its own proposal.
POST/api/v1/matches/{id}/declineThe other side declines. Listings stay open.
POST/api/v1/matches/{id}/completeEither side marks the hand-off done. Both listings become Fulfilled.
POST/api/v1/matches/{id}/cancelEither side cancels; an accepted pair reopens both listings.
POST/api/v1/matches/{id}/messagesSend a message in the thread. Body: text. Not allowed on declined or cancelled connections.

Errors come back as short, human sentences with a standard code: 400 you sent something invalid, 401 you didn’t say who you are, 403 you’re not allowed (“Only the two organizations in this match can access it”), 404 not found, 409 wrong state (“Offer listing is Matched”). Every endpoint is rate-limited per caller.

The real-time feed

EventWho receives itWhen
LIVElisting.createdEveryone connectedA need or offer is posted
LIVElisting.updatedEveryone connectedA listing changes state (matched, fulfilled, reopened)
LIVEmatch.proposed / accepted / declined / completed / cancelledOnly the two organizations in the connectionA connection changes
LIVEmessage.sentOnly the two organizations in the threadA message is sent

An app connects once to /hubs/exchange, says which organization it represents, and then simply receives. This is what makes “Jordan gets alerted” happen without Jordan refreshing anything.

What is real and what is simulated

Real today

The IRS data for all 42,510 WA organizations, loaded into a database. The API above, with matching, connections, messaging and the real-time feed, exercised end-to-end by the command-line demo and 57 automated tests. The 32 organizations in the prototype, with their real EINs, cities and sizes.

Simulated in the prototype

Accounts and sign-in (the prototype pretends), the people (Casey, Jordan), every listing, connection and message, the three example businesses and the community member, and the alerts. The prototype runs the same matching rules in the browser and stores everything only on your device.

Designed, not built yet

Claiming an organization and verifying you belong to it, business and supporter accounts and payments, standing agreements and P-levels in the backend, email/push alerts, the web app itself. See the design brief.

Glossary

501(c)(3)
The section of US tax law for charities. Donations to them are tax-deductible. The IRS decides who qualifies.
EIN
An organization’s permanent nine-digit tax ID. Our primary key.
NTEE
National Taxonomy of Exempt Entities — the letter-plus-number cause code (K31 = food banks).
Database
Structured storage many programs can read and write at once, safely.
API / endpoint
The set of web addresses apps call; each address is an endpoint with one job.
JSON
The text format requests and answers travel in — readable by people and programs alike.
Real-time feed (SignalR)
A connection the server pushes events through, so screens update without refreshing.
Listing / need / offer
One posted item. A need is “we need”; an offer is “we have”.
Connection / match
One need paired with one offer, moving Proposed → Accepted → Completed.
Standing agreement
An accepted recurring pair: weekly, monthly, quarterly or ongoing, with logged deliveries.
P0–P3
Priority levels, from “can’t operate” to “whenever”.
Cluster
Several nearby pins shown as one numbered circle until you zoom in.
ZIP centroid
The center point of a ZIP code area; where a pin sits until street-level geocoding exists.
Acting organization
The organization a request is made on behalf of — today an X-Org-Ein header, later your login.
